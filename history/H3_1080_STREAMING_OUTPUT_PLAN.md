# MiniMax H3 原生 1080p 逐帧输出与流式编码实施计划

**创建日期：** 2026-08-30  
**当前状态：** 已执行（2026-08-30）。5/22/73 帧全部通过；90 帧仍被物理内存阻挡，瓶颈已从 `CreateVideo` 定位到 `VAEDecode` + `ImageScale`。执行结果见第 10 节。  
**目标设备：** RTX 5080 16GB + 31.11GiB 系统内存  
**目标实例：** 独立 ComfyUI 0.34，API `http://127.0.0.1:8189`（实际执行时 Comfy Desktop 将其暴露在 `8188`，见 10.6）  
**关联文档：** [项目使用手册](../README.md)｜[验证历史](VALIDATION_HISTORY.md)

## 1. 当前结论

原先“22 帧可能接近原生 1080p 上限”的判断已经被实测推翻。固定同一输入图、seed、20 步、HMNSFW 0.5、静音、内部 1920×1088、输出 1920×1080，只改变帧数后得到：

| 帧数 | 成片时长 | 总耗时 | VRAM 峰值 | RAM 峰值 | 结果 |
|---:|---:|---:|---:|---:|---|
| 39 | 1.63 秒 | 357.5 秒 | 13.04GiB | 30.08GiB | 成功；39/39、黑帧 0 |
| 56 | 2.33 秒 | 590.4 秒 | 12.98GiB | 30.43GiB | 成功；56/56、黑帧 0 |
| 73 | 3.04 秒 | 874.3 秒 | 12.73GiB | 30.58GiB | 成功；73/73、黑帧 0 |
| 90 | 3.75 秒 | 1190.5 秒后中断 | 12.96GiB | 31.11GiB | `CreateVideo` 触发熔断，无 MP4 |

当前整批视频输出管线的结论是：

- **保守档：39 帧。** 后台程序无法完全清理时优先使用。
- **日常推荐上限：56 帧。** 本次峰值 30.43GiB，仍需串行运行。
- **可完成边界：73 帧。** 峰值 30.58GiB，只剩约 0.53GiB 物理内存，不适合无人值守。
- **首次失败：90 帧。** 系统 RAM 达到 31.11GiB；按计划停止 107/124 帧测试。

90 帧不是 H3 扩散、显存或 VAE 的硬上限。ComfyUI 历史明确记录：中断发生在节点 `14 / CreateVideo`，此前以下节点均已执行：

```text
H3 采样
  → VAEDecode（节点 12）
  → 1920×1088 图像批次
  → ImageScale（运行器动态注入的节点 19）
  → 1920×1080 图像批次
  → CreateVideo（节点 14，RAM 达到 31.11GiB）
  → SaveVideo（节点 15，未执行）
```

因此，90 张 1920×1080 帧当时已经以 ComfyUI IMAGE 张量存在于内存，但没有逐张保存为 PNG。`CreateVideo` 为构造 VIDEO 对象再次持有或转换整批帧，形成末端内存重叠；熔断后这些临时张量被释放，没有留下 90 张图片或 MP4。

## 2. 改造目标

把末端从“整批帧直接交给 `CreateVideo`”改为：

```text
H3 latent
  → VAE 解码
  → 无裁剪缩放至 1920×1080
  → 按运行 ID 逐帧写入隔离目录
  → 确认帧序号、数量、尺寸和完整性
  → 请求 ComfyUI 卸载模型并释放缓存
  → FFmpeg/AV视频编码器顺序读取图片
  → 生成临时 MP4
  → 媒体与逐帧验收
  → 原子发布正式 MP4
```

第一验收目标是让 90 帧完整落盘并输出 3.75 秒 MP4；90 帧通过后再依次测试 107 和 124 帧，直到发现新的真实上限。

本阶段不改变 H3 模型、采样器、提示词、输入图、seed、LoRA 或内部尺寸，确保结论只反映输出方式变化。

## 3. 不变量与安全边界

1. 保留现有 `CreateVideo → SaveVideo` 工作流和 39/56/73 帧证据，不覆盖已有 JSON 或样片。
2. 新工作流、新运行器和新输出目录使用独立名称；尚未通过验收前不替换默认路线。
3. ComfyUI 仍只监听 `127.0.0.1`；不暴露公网 API。
4. 90/107/124 帧均使用 31.0GiB 硬熔断；不取消熔断，不把页面文件当作物理内存。
5. 生成前调用 `/free` 卸载模型和缓存，并确认没有其他大型 LLM、扩散模型或 GPU 任务驻留。
6. 每次只运行一个队列；失败后先确认队列为空、服务可访问，再释放缓存。
7. 帧目录按 Run ID 隔离。正式文件永不覆盖；同名目标存在时必须拒绝或生成新 Run ID。
8. 只有当帧序列和 MP4 均完成验收后，才允许清理临时帧；默认保留失败现场。

## 5. 实施阶段

### 阶段 0：冻结现有证据

- 保留 73 帧成功报告、指标和样片哈希。
- 保留 90 帧失败报告与 ComfyUI 历史中的 `node_id=14 / node_type=CreateVideo`。
- 记录当前工作流节点 12、14、15 及运行器动态节点 19 的连接关系。
- 确认现有 `1080_probe_90` 只作为负对照，不再次用整批视频输出运行。

**通过标准：** 新改造不会修改或覆盖现有证据。

### 阶段 1：建立逐帧输出烟测

- 从现有 API 工作流复制出帧序列版本。
- 移除节点 14 `CreateVideo` 和节点 15 `SaveVideo`。
- 把 1920×1080 的节点 19 输出连接到序列保存节点。
- 文件名使用 `<run-id>/frame_00000.png` 到 `<run-id>/frame_NNNNN.png` 的固定零填充格式。
- 先跑 5 帧，再跑 22 帧；验证没有重复、缺号、乱序或旧帧混入。

**通过标准：**

- 文件数量精确等于请求帧数；
- 序号从 0 连续到 `frames-1`；
- 所有图片均为 1920×1080、可完整解码；
- 黑帧为 0；
- 峰值不高于同帧数旧视频路线。

### 阶段 2：外部流式编码

编码器只按序读取一张或极小批次图片，不一次性加载全目录。固定输出：

- H.264 High；
- 1920×1080；
- 24fps；
- `yuv420p`；
- CRF 18；
- `slow` / `animation`；
- fast-start；
- 无音频。

编码先写入带 `.part.mp4` 的临时文件；完成媒体与逐帧验收后再原子改为正式 `.mp4`。编码失败时保留帧目录和运行报告，不生成看似正式的半文件。

**通过标准：**

- MP4 帧数与 PNG 数量一致；
- FPS、分辨率、像素格式和音轨符合合同；
- PTS 单调，黑帧 0；
- 解码后与 PNG 的 PSNR/MAD 达到现有 CRF 18 编码基线；
- 编码阶段 RAM 不随总帧数线性累积。

### 阶段 3：90 帧正式验证

- 运行前释放 ComfyUI 模型和缓存，记录空闲 RAM/VRAM。
- 固定输入 `keqing_gpt_reference_16x9.png`、seed `2026083022`、20 步、HMNSFW 0.5、静音。
- 生成 90 张 1920×1080 帧并保存运行报告。
- 释放 ComfyUI 缓存后再编码 3.75 秒 MP4。
- 对 PNG 序列和最终 MP4 分别执行数量、黑帧、连续帧、首尾漂移与抽帧复核。

**通过标准：**

- 90/90 PNG 和 90/90 视频帧；
- 生成和编码任一阶段 RAM 均低于 31.0GiB；
- 无页面文件重度换页、OOM、损坏帧或输出中断；
- 最终视频可从头到尾连续解码。

### 阶段 4：继续定位新上限

只有 90 帧完全通过后才继续：

1. 107 帧；
2. 124 帧；
3. 首次失败后停止，不继续向更长帧数冒进。

每档都先清空缓存、使用相同 seed 和配置，并分别记录扩散、帧落盘、释放、编码和验证阶段的资源峰值。不能仅凭总进程峰值判断具体瓶颈。

### 阶段 5：默认档位决策

根据结果分三类固化：

- `recommended`：至少保留 0.75GiB 物理内存余量，可作为日常串行档；
- `boundary`：可以完成，但余量小于 0.75GiB，只用于人工看守；
- `negative_control`：触发熔断或需要页面文件硬撑，只保留证据，不进入日常菜单。

默认档位不单看“能否跑完”，还要考虑总耗时、失败恢复成本和临时帧占用。

## 6. 需要区分的三个内存阶段

运行报告必须分别采样并标记：

1. **扩散阶段：** 模型权重、text encoder、latent 和 offload/pinned memory；现有 90 帧已证明该阶段可完成。
2. **VAE/缩放/落盘阶段：** 解码后的 IMAGE batch 和 1920×1088 → 1920×1080 缩放；需要验证 `SaveImage` 是否增加新的批量副本。
3. **外部编码阶段：** 模型已卸载，编码器只保留有限帧缓冲；目标是峰值与总帧数基本无关。

不能再用单个“整个任务的最高 RAM”推断是哪一阶段失败。报告应包含每个阶段的起止时间、阶段峰值、当前节点和输出计数。

## 7. 失败处理与回滚

- **达到 RAM 熔断：** 调用 `/interrupt`，等待队列清空，保留已写入帧和报告，再调用 `/free`。
- **保存帧中断：** 不补写到原目录；新建 Run ID 重跑，避免新旧帧混合。
- **发现缺帧/乱序：** 禁止编码；报告列出第一个缺失或重复编号。
- **编码失败：** 删除或保留 `.part.mp4` 作为失败证据，但不改名为正式文件；PNG 不删除。
- **验证失败：** 正式 MP4 不发布，保留源帧、临时视频和指标。
- **新路线资源更差：** 保持现有 56 帧日常档与 73 帧边界档，不替换默认路线。

## 9. 最终决策规则

只有在“90 帧逐帧落盘成功 + 外部编码成功 + 逐帧核验通过”三项同时满足后，才能把 90 帧称为可用。仅在内存中完成扩散和 VAE 解码不算交付完成。

### 10.4 90 帧的失败定位

`artifacts/h3_1080_stream_90_20260830T105631Z-0f27_run.json` 的 576 个采样点给出精确位置：

| 时刻 | RAM | VRAM | 已落盘帧 | 事件 |
|---:|---:|---:|---:|---|
| 0–1105 秒 | 28.3–29.5GiB | 2.3–5.7GiB | 0 | H3 采样，平台稳定 |
| 1111 秒 | 29.00GiB | 3.74→11.30GiB | 0 | `VAEDecode` 开始占用显存 |
| 1123→1141 秒 | 29.73→30.14GiB | 10.8GiB | 0 | 1920×1088 批次写入系统内存 |
| 1143→1149 秒 | 30.47→30.91→31.02GiB | 11.4GiB | 0 | `ImageScale` 批次填充中触发熔断 |

`failed_stage` 记为 `sampling_decode_scale`，`SaveImage` 一次都没有执行。因此第 9 节预设的分支成立：**真正瓶颈是节点 12 的 1920×1088 批次与节点 19 的 1920×1080 批次同时驻留**，去掉 `CreateVideo` 是必要的但不充分，瓶颈只是前移了一个节点。按单帧 float32 各约 23.9/23.7MiB 估算，90 帧两批共约 4.18GiB，缺口约 1.5–2GiB。

### 10.5 执行中发现并修复的问题

**输入缩放模式不一致（已修复）。** 从基础工作流复制出的节点 17 带着 `crop: "center"`，而 `run_h3_live2d_profile.ps1` 会在提交前把 1080p 档位强制改成 `disabled`。首帧不同，同一个 seed 就会走出不同的生成轨迹。定位方式是从旧 22 帧成片里取出 ComfyUI 嵌入的 workflow 元数据逐节点 diff，除输出尾部外唯一差异就是这一项。现已在工作流 JSON 与运行器两处改为 `disabled`，并把 `17.crop`、`19.crop` 和两个 `upscale_method` 写进运行报告，以后仅凭报告即可发现同类偏差。带 `center` 跑出的三次结果已删除，不作为证据保留。

**运行器被杀后 ComfyUI 继续跑（已修复）。** 熔断逻辑原本只存在于监控进程里。执行期间 90 帧链条被外部中止一次，运行器消失而 ComfyUI 仍在执行 prompt，RAM 停在 29.21GiB 且没有任何熔断看守——正是第 3 节不变量 4 禁止的状态。修复分两层：运行器的监控循环包进 `try/finally`，覆盖正常退出、异常与 Ctrl+C；硬杀进程时 `finally` 不执行，由 `h3_stream_watchdog.ps1` 兜住。守护进程只在 ComfyUI 报告的运行中 prompt 正是自己那一个时才中断，并比对父进程启动时间以避免 PID 复用误判。已用硬杀实测：运行器 `Stop-Process -Force` 后 6 秒宽限期满即中断，队列清空，日志写入 `artifacts/h3_1080_stream_watchdog_<run-id>.log`。

### 10.7 编码合同与保真度基线

三档成片全部满足合同：H.264 High、1920×1080、24fps、`yuv420p`、CRF 18、`slow`/`animation`、fast-start、仅视频流、PTS 单调且步长稳定。与源 PNG 的偏差首次在本项目留下实测基线：

| 5 帧 | 40.69 / 40.04 dB | 37.59 dB | 2.3416 | `df98b751f580eaa3c48e776693c36e31f210d67f270e6da5c3befebb46bb974b` |
| 22 帧 | 40.93 / 40.19 dB | 38.15 dB | 2.2316 | `8a1459e65a78910d962f136e29498b2ee8283a492fd468644e2e153b897c835b` |

门槛按实测值下方设定：luma PSNR ≥ 38dB 为主判据，RGB PSNR ≥ 34dB 与 MAD ≤ 3.5 为辅。选 luma 作主判据是因为 4:2:0 色度下采样会压低 RGB 域数值，而它对两条路线是同样的、不可避免的。

### 10.8 输出级中性如何成立

逐帧路线与整批路线的像素一致性**不能**用 PSNR 对比证明。对 73 帧逐帧剖面显示，与旧成片的差距随帧号单调下滑并饱和：首帧 33.15dB，第 8 帧 26.53dB，第 32 帧 23.09dB，之后稳定在约 22.6dB / MAD 7.6。编码损耗不会随帧号递增，这是生成轨迹分叉。

成立的依据是另外三条：

1. 旧成片内嵌的 workflow 与新工作流逐节点一致（节点 1–19 完全相同，仅输出尾部不同）；
2. 同会话同参数重跑 bit 级相同——5 帧连跑两次成片 SHA-256 一致，PNG 像素 MAD 0.0000（PNG 文件字节不同仅因 `SaveImage` 把含 run-id 的 workflow 写入了 PNG 元数据）；
3. `SaveImage` 只读取节点 19 产出的 IMAGE 张量且无法回写，因此它写下的帧就是旧路线交给 `CreateVideo` 的同一批张量，输出级中性在构造上成立。

由此得到一个对项目有实际影响的副产物结论：**同 seed 不保证跨 ComfyUI 会话拿到同一条母版**。已归档的 39/56/73 帧样片无法从新会话按字节复现，最可能的原因是内存压力驱动的权重卸载与后端选择在不同空闲内存下作出不同决策，改变了浮点累加顺序。换机器或重启实例后，母版应重新人工复核而不是假定与旧样片相同。

### 10.9 峰值 RAM 与后台基线基本无关

这次四次运行的空闲基线在 5.88–11.00GiB 之间变动，但采样平台始终停在 28.3–29.5GiB。原因在 ComfyUI 0.34 的 `RAM_PRESSURE` 缓存按物理内存自适应（`cache_ram = min(10, max(2, total_ram×0.10))`，`cache_ram_inactive = total_ram`），腾出的后台内存大部分被它拿去多缓存，没有变成末端可用余量。因此「关掉后台程序再跑」对这一瓶颈基本无效，不能作为让 90 帧通过的手段。

### 10.10 档位分级与结论

按第 5 节规则（`recommended` 需至少 0.75GiB 余量）：

- `recommended`：5 帧（2.05GiB）、22 帧（2.00GiB）、73 帧（0.93GiB）；
- `negative_control`：90 帧（0.09GiB，中断且无帧落盘）。

73 帧虽然按规则判为 `recommended`，但只高出门槛 0.18GiB，仍不建议无人值守；README 继续把 56 帧作为日常上限、73 帧作为需要看守的边界档。逐帧路线的真实收益不在解锁更长片段，而在于把输出阶段的内存占用从「随帧数线性增长」变成「与帧数无关」，并让失败现场可检查：帧序列留在盘上，缺帧、乱序、黑帧都能在编码前拦住。
