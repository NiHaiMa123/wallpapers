# H3 1080p 循环壁纸：已定案为镜像回放

**创建日期：** 2026-08-30
**定案日期：** 2026-08-30
**当前状态：** 循环方式已锁定为镜像回放（`0..N-1` 接 `N-2..1`）。提示词、编码器和筛选指标已改完。待做：用新提示词筛 seed，前两名上 1080p 73 帧再镜像。
**前置结论：** [H3 1080p 逐帧输出与流式编码实施计划](H3_1080_STREAMING_OUTPUT_PLAN.md) 已执行完毕（5/22/73 帧通过，90 帧被内存阻挡）
**关联文档：** [项目使用手册](../README.md)｜[验证历史](VALIDATION_HISTORY.md)

## 0. 定案

采用**镜像回放**，不采用交叉融合作为 1080p 壁纸的默认闭环。插帧只作为通过人工复核之后的可选后处理，顺序固定为先插帧、后镜像。

原因（第 4 节的评估没有变）：

- 本机原生 1080p 上限是 73 帧 = 3.04 秒。镜像后周期 144 帧 = 6.00 秒，速度不变，不多花生成内存。
- 首尾相接在构造上成立，不需要交叉融合，也不需要模型把末帧精确送回起点。
- 「闭眼再正确睁开」降级成「闭眼」，睁开由回程免费给出。
- 交叉融合过不了花瓣单向位移；镜像把重力破绽换成回程上飞，所以花瓣仍然必须在提示词里锚死，不能指望后期救。

眨眼放在**前向段约 40%**，不放在转折点。6 秒周期里会出现两次镜像眨眼：约 1.2 秒和 4.8 秒各一次，间隔约 3.6 秒 / 2.4 秒。先前笔记写成「间隔 1.2 秒再 4.8 秒不眨」是把 40% 误算到了整个 6 秒周期上，已纠正。两次间隔都落在自然眨眼 2–6 秒的范围内。

现有 73 帧样片（`1080_stream_73`）仍不可作母版：它用的是可行性测试提示词，花瓣在落、水晶带在动、眼睛几乎未闭。它只用来验证镜像编码器和转折点指标。

## 1. 触发这次讨论的事实

用户对唯一足够长可看的样片（`1080_stream_73`，3.04 秒）做了人工动态复核，报告四个缺陷：

1. 首尾不相接，不是循环；
2. 花瓣在下落，3 秒的单向运动不可能循环；
3. 眼睛没有完全闭上；
4. 底座前景的水晶带被当成头发在动。

缺陷 2 和 3 的直接原因是提示词。该样片用的是 `prompts/MINIMAX_H3_1080P_FEASIBILITY_PROMPT.md`，它本来是 1080p 可行性测试提示词，不是壁纸母版提示词：正文写 `Keep both eyes open`、Avoid 列表含 `blinking during this short test`，同时明确要求 `faint coordinated movement in flower petals and violet electro particles` 却没有要求周期性归位。缺陷 1 的原因是该提示词完全没有循环时序约束，且没有跑 12 帧交叉融合。缺陷 4 的原因是提示词锚定了头、躯干、手，但对前景那条半透明紫水晶带只字未提，而它的色调与材质与角色飘带几乎一致，被归入了「头发/飘带次级运动」组。

**一个必须记住的教训：** 交叉融合大概能把边界 MAD 压到 4K 门槛 `endpoint_boundary_mad_max: 2.3` 以下，但花瓣的单向位移会以重影形式留在画面里。**现有 4K 验收门槛会放过一个用户仍然会否决的视频。** 镜像回放同样会让这条门槛失去信息量，见第 5 节。

## 2. 硬约束

- 原生 1080p 在本机的上限是 **73 帧 = 3.04 秒**。两条输出路线都在 90 帧失败，瓶颈是 `VAEDecode` 的 1920×1088 批次与 `ImageScale` 的 1920×1080 批次同时驻留，缺口 1.5–2GiB。
- 已验证档位与峰值：39 帧 30.08GiB、56 帧 30.43GiB、73 帧 30.18GiB（逐帧流式路线）。
- H3 合法帧长为 `5 + 17k`：5、22、39、56、73、90、107、124。
- 峰值 RAM 与后台基线基本无关，关后台程序不能换来末端余量。

## 3. 方案 A：后期插帧（降为通过后的可选项）

### 3.1 概念前提

插帧**不增加时长**，只增加帧密度。39 帧 ×2 = 77 帧，覆盖的仍是同样的 1.63 秒内容。按 48fps 播是更顺滑的 1.63 秒；按 24fps 播是 3.21 秒但**动作变成半速**。因此「用插帧换时长」只在接受动作放慢时成立。镜像回放已经用正常速度换到 6 秒，插帧不再承担加时长的任务。

### 3.2 本地已有能力

ComfyUI 0.34 自带原生插帧，无需第三方节点：

| 节点 | 说明 |
|---|---|
| `FrameInterpolationModelLoader` | 同时支持 RIFE(IFNet) 与 FILM(FILMNet)，自动识别权重格式 |
| `FrameInterpolate` | multiplier 2–16 |
| `OpticalFlowLoader` | 存在但无任何模型（RAFT 未安装，选项为空） |

`models\frame_interpolation\rife_v4.26.safetensors`（21.6MB）已在位。FILM 只需放入权重即可用。实现在 `comfy_extras/nodes_frame_interpolation.py`（208 行），模型代码在 `comfy_extras/frame_interpolation_models/{ifnet,film_net}.py`。

### 3.3 读源码得到的三个关键事实

**一次性分配整个输出批次。** `torch.empty((total_out_frames, 3, H, W))` 落在 CPU 内存。73 帧 ×2 = 145 帧 1920×1080 float32 = 3.61GiB，加输入批次 1.81GiB。**因此插帧绝对不能与 H3 生成放在同一个 prompt 里**，那正好撞上第 2 节那道墙。作为独立的第二个 job（H3 已卸载、基线约 7–9GiB）则放得下：×2 约 3.6GiB、×3 约 5.4GiB、×4 约 7.2GiB。

**RIFE 有 `forward_multi_timestep`。** 光流只算一次即可生成所有中间时刻，且相邻帧对之间缓存特征，所以 ×4 远比跑四遍便宜；OOM 时自动减半批次重试。

**`FrameInterpolate` 只在批次内部插值，不绕回。** 输出 `(N-1)×k+1` 帧。要闭环需手工构造：喂 `[0..N-1, 0]` 共 N+1 帧 → ×k → `N×k+1` 帧 → 丢最后一帧 → `N×k` 帧闭合循环。镜像回放让这个绕回技巧变得不必要。

### 3.4 输入端的麻烦

`LoadImageDataSetFromFolder` 只列 ComfyUI **input** 目录下的子文件夹，而流式路线把 PNG 写在 **output** 目录。要么把帧目录拷进 input（73 帧 218MB），要么用 `LoadVideo` + `GetVideoComponents` 读 MP4（但那是有损帧）。

**未验证的风险：** 该节点属于 `comfy_extras.nodes_dataset`，描述说返回「list of images」，**排序行为尚未验证**。插帧对帧序零容错，使用前必须先确认排序稳定且为数字序。

### 3.5 风险

项目里 RIFE 已经失败过一次（`VALIDATION_HISTORY` §10.2），但失败原因完全不同：当时输入是 Krea2 重画的手工关键帧，人物在关键帧之间被改了，结论是「RIFE 只会插值，不会修复错误关键帧」。H3 生成的帧本身时序连贯，是插帧的合适输入，那条负面结论**不能**直接套用。

真正的风险集中在用户抱怨的元素上：光流对**出现/消失的小粒子**（花瓣、电弧）和**半透明发光物**（水晶带、灯焰）处理最差，粒子没有连续轨迹可跟。插帧可能让花瓣重影更明显而非更轻。眨眼是 2–4 帧快动作，跨眨眼插帧的经典失败是半透明鬼影眼皮。

## 4. 方案 B：镜像回放（已采用）

### 4.1 核心价值

正确帧序为 `0..N-1` 接 `N-2..1`，周期 `2N-2`。首尾相接**在构造上成立**，不需要任何交叉融合。

| 生成帧数 | 已验证内存 | 镜像后周期 | 24fps 时长 | 动作速度 |
|---:|---:|---:|---:|---|
| 39 | 30.08GiB | 76 | 3.17 秒 | 正常 |
| 56 | 30.43GiB | 110 | 4.58 秒 | 正常 |
| 73 | 30.18GiB | 144 | **6.00 秒** | 正常 |

用已跑通的 73 帧即可得到 6 秒正常速度完美循环，不多花一分内存，生成时间仍是 837 秒。原路线要 3.75 秒需跑 90 帧而跑不通。插帧要 6 秒得接受半速，镜像不用。

**实现陷阱：** 写成 `0..N-1` 接 `N-1..0` 会让首尾各重复一帧，两个转折点各卡顿两帧。索引函数在 `scripts/loop_common.py`。

### 4.2 它解决了模型最不擅长的那一步

镜像把「闭眼再正确睁开」降级成「闭眼」，睁开免费且保证对称。项目里「回到起始状态」失败过两次：§5.3 的 1344×768×124 帧成片「后半段闭眼后未在末帧前睁开」；§10.3 的原生首尾闭环「闭眼覆盖约中间一半视频」。73 帧那条 endpoint MAD 5.36 同源。单向走到极值对扩散模型远比精确回到起点友好。

### 4.3 对四个缺陷的实际效果

| 缺陷 | 镜像回放的效果 |
|---|---|
| 首尾不相接 | **构造上解决**，边界 MAD 从 5.36 降到自然相邻帧量级（实测约 1.1） |
| 花瓣落下 | 技术上解决，但回程花瓣往上飞。重力不可逆，这是镜像唯一无法掩盖的破绽 |
| 眼睛没完全闭上 | **最大受益点** |
| 水晶带被当成头发 | **无帮助**，属提示词锚定问题 |

**别指望镜像救单向运动**，它只是把破绽换了形式。花瓣仍按 `keqing_h3_1080_loop_anchored_en.txt` 的写法完全锚住。

### 4.4 真正的代价：两个转折点

即使帧序正确，速度在两个转折点归零反向，这是 Boomerang 类循环最典型的破绽。只有转折帧恰好是所有运动元素的自然极值时才隐形。帧 0 天然是极值（输入图、静止），问题是帧 N-1 需要让每个运动元素同时处于极值。

两个取舍：

- **眨眼放在转折点。** 闭合眼皮是完美极值，一周期一次干净眨眼。但闭合过程会占满整个 3 秒段，看起来像打瞌睡；除非眨眼只占最后几帧，而那时呼吸与头发处于任意相位。
- **眨眼放在段中间。** 一周期出现两次镜像眨眼。**已采用此方案。** 73 帧、24fps、眨眼在前向段 40%：正向约第 29 帧（1.2 秒），回程约第 115 帧（4.8 秒）。间隔 3.6 秒与 2.4 秒，都比「连眨两下再停 4.8 秒」更自然。

可放心的两点：阻尼振荡倒放变成振幅递增，理论上不自然但幅度极小；灯焰闪烁与水面反光是随机的，倒放测不出来。

相邻帧一阶 MAD 在转折点**不会**出现尖峰：`…, 71, 72, 71, …` 的两步就是同一对源帧的正反播放。可见顿挫是二阶差分（加速度反向），代理量为 `2 × 最后一步 MAD`。筛选指标用 `motion_step_last_ratio = 最后一步 / 全程均值`，越接近 0 越说明末帧已经停住。

### 4.5 与插帧的先后顺序

**先插帧，后镜像。** 反之转折点包含运动方向反转，正是光流最易崩的位置；且先镜像会让插帧在重复内容上白做一倍功。

## 5. 验收指标的连带影响

镜像回放会让现有指标**失去信息量**：4K 门槛 `endpoint_boundary_mad_max: 2.3` 被轻松通过，而镜像的新失效模式一个都不在现有指标里。

- **转折点顿挫可测**：`motion_step_last_ratio` 和 `turn_jerk_proxy_mad`。需要人眼确认阈值是否有区分度。
- **倒放物理无法自动测**，只能靠人眼。花瓣上飞、呼吸倒放目前没有代理指标。
- 4K 验收在镜像母版上不应再把 `endpoint_boundary_mad_max: 2.3` 当作质量信号，它几乎一定通过。

## 6. 已落地的代码

- `scripts/loop_common.py`：`playback_indices(n, "mirror")` → `0..N-1` 接 `N-2..1`。`tests/test_mirror_playback.py` 锁死 73→144 的转折点与尾帧不含 0。
- `scripts/encode_h3_frame_sequence.py --loop-mode mirror`：对已有 PNG 序列做索引算术后流式编码，仍是一帧一打开，不把 144 帧驻留内存。默认 `linear`，1080p 流式生成器行为不变。
- `scripts/build_seamless_wallpaper.py --mode mirror`：给 576p 草稿预览用。默认仍是 `crossfade`，4K 旧链路不受影响。
- `scripts/screen_h3_loop_candidates.py --loop-mode mirror`（现为默认）：`loop_score` 不再计入 `endpoint_full_mad`；改为惩罚水晶带运动、地面花瓣位移、末帧速度比、眨眼不足、眨眼落在边界、末帧眼睛未睁。`--loop-mode return` 保留旧判据。
- `prompts/keqing_h3_1080_loop_anchored_en.txt` 已改成「单向走到极值」：首帧静止睁眼、末帧所有运动元素同时处于极值、眨眼在约 40%、花瓣禁止下落、水晶带仍是嵌入地面的刚性玻璃。

- 73 → 144 帧，6.00 秒，H.264 High 1920×1080 24fps，文件 `outputs/h3_1080_stream/live2d_1080_stream_i2v_1920x1080_73f_mirror144_s050_seed2026083022_keqing_gpt_reference_16x_silent_20260830T111922Z-730c.mp4`

## 7. 外部 VFI 调研（原中断项，已补完）

调研日期 2026-08-30。结论：**现在不值得引入 FILM 或 GIMM-VFI。** 本机 RIFE 4.26 已经是 Practical-RIFE 公开线的顶端；插帧仍然只做「先插后镜」的后处理，且必须等一条人工通过的镜像循环。

| 问题 | 结论 |
|---|---|
| RIFE 4.26 之后有没有更好的公开版 | **没有。** [Practical-RIFE](https://github.com/hzwer/Practical-RIFE) 最新权重停在 4.26（2024-09-21）。作者默认推荐 4.25（「大多数场景」；4.25 对动画「明显改善」）；4.24+ 被作者点名为部分扩散视频后处理合适。社区有人更喜欢 4.18/4.25，有人测 4.26.heavy。ComfyUI-VFI 的 rife47/rife49 是 Fannovel16 的旧编号，不是 4.7/4.9 之后的新架构。本机 `rife_v4.26.safetensors` 就是当前可装的天花板。 |
| GIMM-VFI | NeurIPS 2024，任意时刻连续插值。[官方仓库](https://github.com/GSeanCDAT/GIMM-VFI) 依赖 CuPy / 较老的 PyTorch 1.13；Windows 实用路径是 [kijai/ComfyUI-GIMM-VFI](https://github.com/kijai/ComfyUI-GIMM-VFI)，这是 0.34 测试实例上尚未安装的第三方节点。社区评价对大位移优于 RIFE，但「慢好几倍」。官方 2K×8 约 7.9GiB、4K×8 约 10.9GiB VRAM（`DS_SCALE` 0.5/0.25）。1080p 全分辨率未给出官方数。本机 `OpticalFlowLoader` 仍无 RAFT 权重。 |
| FILM 1080p / Windows | 0.34 原生 `FILMNet` 可用，缺的只是权重。Fannovel16 的 FILM VFI 在高分辨率上以 RAM/VRAM 吃紧出名，社区做法是切段。原生 `FrameInterpolate` 仍一次性分配整个输出批次（第 3.3 节），与 H3 同 prompt 不可行。 |
| 细线条 / 粒子 / 发光 / 眨眼 | 光流类方法的经典失效面。SG-RIFE（2025）仍把「大位移与遮挡」写成 RIFE 的未解决问题。眼皮是对虹膜的快速遮挡，中间帧容易半透明鬼影；花瓣和电弧没有可跟踪的连续轨迹。没有找到可信反例说「新模型已经解决眨眼鬼影」。 |
| 循环绕回插值的现成工具 | 没有需要的专用工具。原生节点不绕回。手工喂 `[0..N-1, 0]` 再丢末帧即可，但镜像路线不需要这一步。 |
| DLSS / FSR / AFMF 类比 | **不成立。** 它们是游戏引擎用真运动矢量做的实时插帧，带输入延迟，不能离线吃 PNG 序列。H3 帧只有估计光流，没有引擎 MV。质量类比不能当证据。 |
| 「少生成多插帧」vs 原生生成 | 插帧不增加内容时长，只增加帧密度。原生多出来的帧带扩散模型自己的时间信息；插帧无法发明正确的重力或一次完整眨眼。本项目 73 帧已经是内存上限，插帧只能把 3.04 秒变得更顺，不能替代镜像去换 6 秒。 |

因此：不在 0.34 测试实例上安装 GIMM-VFI；不把 FILM 纳入默认链路；RIFE 4.26 留作人工通过镜像循环之后的可选 ×2/×4。粒子区和眨眼区必须单独复核。
